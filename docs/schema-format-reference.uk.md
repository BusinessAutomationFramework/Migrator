# Довідник `schema.yaml`

Один YAML-файл на кожне завдання переносу, завантажується
`migrator.schema.load_schema()`. Завдання адресується як `<корінь>:<завдання>`
(див. `migrator.config.yaml`), і його схема резолвиться у
`<шлях кореня>/<завдання>/schema.yaml`.

Реальний робочий приклад, на який посилаються нижче -
`D:\Bukovel\Transfer\warehouse\schema.yaml` (завдання
`bukovel-legacy:warehouse`) - він НЕ в цьому репозиторії (цей корінь завдань
свідомо зовнішній), але ті самі поля стосуються будь-якого завдання,
зареєстрованого під `TransferDATA/` всередині цього репозиторію.

## Поля верхнього рівня

```yaml
schema_version: 1
task: warehouse
kind: Справочник        # "Справочник" | "Документ"
name: Склады
description: "Вільний текст - що переносить це завдання і чому."
```

## `source` - звідки читаються рядки

```yaml
source:
  connection: com        # наразі підтримується лише "com"
  connection_string: 'Srvr="REN-SER-DB1";Ref="TEST_SKI_HIRE";'
```

Читання завжди йде через `com_query.ps1` (окремий 32-бітний процес
PowerShell) - див. [architecture.uk.md](architecture.uk.md).

## `destination` - куди пишуться рядки

```yaml
destination:
  connection: bridge     # наразі підтримується лише "bridge"
  platform_exe: 'D:\Programs\BAF\8.3.23.2299\bin\1cv8.exe'
  connect_args: ["/F", 'D:\Bukovel\EDT_BASE\SKI']   # або ["/S", "сервер\\база"]
```

`platform_exe`/`connect_args` опційні - якщо не задано, рушій використовує
`bridge_client.DEV` (типовий приймач пілотного розгортання).

## `select_mode` - які поля читаються

- `all` (за замовчуванням, рекомендовано) - `ВЫБРАТЬ * ИЗ <Вид>.<Ім'я>`.
  Безпечно: читається КОЖНЕ поле джерела, нічого не пропускається мовчки
  через неповний `field_mappings`.
- `explicit` - будує явний перелік колонок з `field_mappings` (плюс завжди
  обов'язкові системні поля: `Ссылка`, а для довідників ще
  `ЭтоГруппа`/`Родитель`/`Предопределенный`/`ИмяПредопределенныхДанных`).
  Використовуйте лише коли СВІДОМО хочете обмежити, що читається.

## `field_mappings` - транспортна схема "Схема 1 <-> Схема 2"

Це саме той мапінг полів, який просив користувач: стабільний внутрішній
`id`, ім'я поля у джерелі, ім'я у приймачі (зазвичай однакові - обидві
сторони переважно той самий базовий BAF-конфіг, лише різні середовища), і
опис для людини.

```yaml
field_mappings:
  - id: warehouse_type
    source_field: ТипСклада
    destination_field: ТипСклада
    description: "Вид складу - значення переліку ТипыСкладов."
  - id: price_kind_retail
    source_field: РозничныйВидЦены
    destination_field: РозничныйВидЦены
    description: "Роздрібний вид ціни - посилання на Справочник.ВидыЦен."
```

НЕ потрібно перелічувати тут КОЖНЕ поле - лише ті, що варто задокументувати,
перейменувати, чи на які згодом навішується розширення. Решта переноситься
1:1, поки `select_mode: all` (за замовчуванням).

## `related_catalogs` - каскадування до пов'язаних довідників

Кожне правило спрацьовує ЛИШЕ якщо його `ref_type` реально трапляється (як
обгортка `__ref_type__`) десь у вибраних рядках - незадіяні правила просто
пропускаються, дешево.

```yaml
related_catalogs:
  - ref_type: Справочник.ВидыЦен
    detail: reference_only   # "reference_only" | "full"
    depth: 1
    description: "Види цін, на які посилаються склади."
```

- `reference_only` - переносить ВЕСЬ пов'язаний довідник ОДИН РАЗ (без
  подальшого каскадування ЙОГО ВЛАСНИХ пов'язаних довідників). Свідомо
  просто: такі довідники зазвичай невеликі довідники-переліки, а фільтрація
  лише за референсними UUID вимагала б параметризованих COM-запитів без
  реальної користі на такому масштабі.
- `full` - рекурсивно проганяє весь рушій ще на один рівень глибше для того
  довідника (сам знову підпадає під `related_catalogs`/глибину).
- `depth` обмежує, скільки рівнів `full` дозволено перш ніж правило
  пропускається (логується, не помилка).
- Правило, що посилається на САМ довідник завдання (само-посилання) -
  автоматично холостий хід: поточний довідник позначається відвіданим ще
  ДО оцінки правил каскадування.

Скористайтесь `python -m migrator suggest <корінь>:<завдання> [--sample N]`,
щоб отримати початковий перелік усіх `__ref_type__`, що реально трапились у
вибірці - перегляньте і скопіюйте потрібні у `related_catalogs`.

## `tabular_parts` - табличні частини

```yaml
tabular_parts:
  - name: ДоступныеУслуги
    description: "Послуги (Номенклатура), доступні на цьому складі."
```

Кожна заявлена назва підвантажується ОКРЕМИМ запитом
(`ВЫБРАТЬ * ИЗ <Вид>.<Ім'я>.<ІмяТЧ>`) і вкладається у власний рядок ПЕРЕД
записом. При записі `ЗаписатиЕлементи` розпізнає, що ключ - таблична
частина (за метаданими об'єкта, не за назвою-конвенцією) і ПОВНІСТЮ
перезаписує її рядки (Очистить + Добавить наново) - джерело є єдиним
джерелом істини для складу табличної частини.

## `destination_write_options` - обхідні прапорці при записі

```yaml
destination_write_options:
  additional_properties:
    ПропуститьОбновлениеФлагаКонтроляОперативныхОстатков: true
```

Стає записами `Объект.ДополнительныеСвойства` ПРЯМО ПЕРЕД `Записать()` на
боці приймача - загальний механізм для прапорців "пропустити дорогий/
специфічний для бізнес-логіки перерахунок під час імпорту", які може
підтримувати код цільової бази. ЯКІ саме прапорці існують і що вони роблять
- бізнес-логіка приймача, не те, що Migrator хардкодить.

## `hooks` - точки розширення пайплайна

```yaml
hooks:
  - stage: before_read     # before_read | before_write | after_each_item | after_write
    name: log_query
  - stage: before_write
    name: require_fields
    args:
      fields: [Наименование]
  - stage: after_write
    name: print_summary
```

`name` має бути зареєстроване у `migrator/hooks.py` (`@hooks.register("...")`).
Вбудовані: `log_query` (before_read), `require_fields` (before_write -
попереджає, НЕ блокує, про порожні обов'язкові поля), `log_progress`
(after_each_item), `print_summary` (after_write). Заявлення БУДЬ-ЯКОГО
хука `after_each_item` перемикає рушій з одного пакетного запису на запис
по одному рядку (потрібно для справжньої пооб'єктної гранулярності -
повільніше, бо кожен рядок - свій окремий обмін з BridgeTool).
