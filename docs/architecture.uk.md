# Архітектура

## Чому два інтерфейси

Migrator переносить довідники/документи між двома базами 1С:Підприємство:
**джерелом** (у пілотному розгортанні - серверна база, доступна лише по
мережі) і **приймачем** (локальна файлова база). Свідомо використовуються
ДВА різні інтерфейси:

- **COM** (`BridgeTool/com_query.ps1`) читає з джерела. Виконується як
  окремий 32-бітний процес PowerShell (`V83.COMConnector` зареєстрований
  лише 32-біт) і НІКОЛИ нічого не записує - read-only за конструкцією.
- **BridgeTool** (`BridgeTool/BridgeTool.epf`) пише у приймач. Це класична
  зовнішня обробка, яка відкриває базу-приймач як звичайний клієнт 1С і
  лишається запущеною, опитуючи невелику папку обміну на нові запити.
  **BridgeTool НІКОЛИ не встановлює зовнішніх з'єднань** - він спілкується
  лише зі своєю (приймальною) базою.

Такий розподіл існує тому, що зовнішній обробці небезпечно давати рядок
з'єднання до довільної віддаленої бази (обмеження безпечного режиму,
ризик витоку облікових даних, і немає чистого способу гарантувати, що вона
ніколи ні до чого іншого не звернеться). Тримаючи BridgeTool "лише
приймач", а всі читання джерела - у повністю окремому процесі, питання
"куди цей компонент може дотягнутись" стає тривіальним.

```
   База TEST (сервер)                     База DEV (файлова)
        |                                         |
        |  COM (лише читання)                     |  BridgeTool.epf (читання/запис)
        v                                         v
  com_query.ps1  <---- керується через ---->  bridge_client.Bridge1C
      (32-бітний PowerShell)                  (постійна сесія 1cv8.exe)
                          \                    /
                           \                  /
                          migrator.engine.TransferEngine
                                    ^
                                    |
                          migrator.schema.TransferSchema
                              (schema.yaml на кожне завдання)
```

## Протокол обміну (Python <-> BridgeTool)

`ЗапускПараметр()` недоступна зовнішнім обробкам у безпечному режимі
виконання 1С, тому аргументи командного рядка не можуть дістатись
BridgeTool при старті. Натомість:

1. `Bridge1C.start()` (`BridgeTool/bridge_client.py`) пише невеликий
   bootstrap-текстовий файл (`BridgeTool/_launch_config.txt`, один
   фіксований шлях) з двома рядками: папка обміну, і (опційно) папка, куди
   BridgeTool сам пише лог свого життєвого циклу запуску.
2. Потім запускає `1cv8.exe ENTERPRISE ... /Execute"BridgeTool.epf"` як ОДИН
   рядок команди (не список аргументів - `list2cmdline` і власний
   токенізатор PowerShell обидва спотворюють вкладені лапки типу `/F"шлях"`
   інакше).
3. Форма BridgeTool (`Forms/Форма/Ext/Form/Module.bsl`) читає цей bootstrap-
   файл у `ПриОткрытии`, пише `ready.txt` у папку обміну в момент, коли вона
   справді готова приймати запити, і запускає цикл опитування раз на
   секунду (`ПодключитьОбработчикОжидания`).
4. Кожен запит - це файл `request.json` (`{"expression": "..."}` - будь-
   який вираз BSL, обчислюється через `Вычислить()`); BridgeTool видаляє
   його, обчислює через `ОбробитиТекстКоманди` в `Ext/ObjectModule.bsl`, і
   пише `request.json.result.json`.
5. `stop.txt` сигналізує ШТАТНЕ завершення (`ЗавершитьРаботуСистемы`)
   замість вбивання процесу, щоб файлова база коректно звільнила блокування.

Одна сесія BridgeTool обслуговує БАГАТО запитів - вона НЕ перезапускається
на кожен виклик (холодний старт - ~20с). `TransferEngine` тримає ОДНУ сесію
відкритою на весь каскад (головний довідник + все, що з нього каскадується).

## Універсальні примітиви, не бізнес-логіка

`ObjectModule.bsl` навмисно надає лише ДВІ загальні операції, обидві
застосовні до БУДЬ-ЯКОГО довідника/документа за назвою:

- `ВыполнитьЗапрос(ТекстЗапроса)` - виконати довільний запит 1С у
  локальній (приймальній) базі, повернути рядки як JSON.
- `ЗаписатиЕлементи(ВидОбъекта, ИмяОбъекта, JSONРядки, ...)` - записати
  (за UUID) рядки в довідник/документ. Обробляє порядок створення груп/
  елементів, пошук предопределених елементів, приведення типів по полях,
  табличні частини, і обхідний мішок `additional_properties` - див.
  [schema-format-reference.uk.md](schema-format-reference.uk.md), як саме
  схема завдання керує кожним з цього.

ЯКІ довідники переносити, у якому порядку, з яким мапінгом полів - нічого
з цього не живе у BSL. Це декларується схемою у Python
(`migrator/schema.py`, `migrator/engine.py`), тож ці два універсальні
примітиви ніколи не потребують зміни при додаванні нового завдання переносу.

## Конвеєр рушія

`migrator.engine.TransferEngine.run()`, маючи `TransferSchema`:

1. Будує `SELECT` (`TransferSchema.select_query()` - або `SELECT *`, або
   явний перелік колонок з `field_mappings`).
2. Виконує хуки `before_read`, читає через COM (опційно - підвантажуючи
   заявлені `tabular_parts` окремими запитами, вкладеними у кожен рядок).
3. Виконує хуки `before_write`, пише через BridgeTool (`ЗаписатиЕлементи`,
   передаючи `destination_write_options.additional_properties`).
4. Виконує хуки `after_write`.
5. Дивиться, які правила `related_catalogs` реально спрацювали (їхній
   `__ref_type__` дійсно трапився у вибраних рядках -
   `migrator.cascade.plan_cascade`), і рекурсивно переносить кожен - у ТІЙ
   САМІЙ сесії BridgeTool. `reference_only` переносить весь пов'язаний
   довідник цілком, один раз (це, як правило, невеликі довідники-переліки);
   `full` рекурсивно проганяє рушій ще на один рівень глибше, знову з
   урахуванням власних `related_catalogs`/глибини.

Повний довідник полів `schema.yaml` - у
[schema-format-reference.uk.md](schema-format-reference.uk.md), а веб-панель,
що керує всім цим без термінала - у [gui.uk.md](gui.uk.md).
